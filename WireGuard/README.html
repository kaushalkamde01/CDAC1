WireGuard VPN — Hybrid SOC Infrastructure

Secure site-to-cloud VPN interconnecting distributed Linux and Windows virtual machines across multiple private networks, gatewayed through a single AWS EC2 WireGuard server — tunneled over HTTPS via WSTunnel where UDP is blocked.

VPN Server
AWS EC2 · Ubuntu 22.04
Public Endpoint
13.205.137.92
Interface
wg0 · UDP 51820
Transport Fallback
WSTunnel over TCP 443
One WireGuard interface, three logical subnets, one gateway — click a phase in the sidebar to jump to its setup steps.
01

Objective & Architecture

A lightweight, secure Layer-3 VPN interconnecting all SOC lab infrastructure over a single encrypted network.

What it secures

Communication between cloud and on-premises infrastructure, eliminating direct exposure of internal services.

What it enables

Private access to SOC components, and communication between multiple isolated internal networks via one centralized gateway.

Secure cloud ↔ on-prem No direct service exposure Private SOC component access Cross-network communication Centralized AWS gateway

04

Cryptography

WireGuard provides all of this automatically via the Noise protocol framework — no manual key exchange ceremony required beyond distributing public keys.

Public-key authentication Private-key encryption Modern authenticated encryption Perfect Forward Secrecy

Each peer holds a private key (kept secret) and a public key (shared with the server). The server identifies every client exclusively by its public key — there are no shared secrets or usernames/passwords at the WireGuard layer.

P1

WireGuard Server Configuration (AWS EC2)

Provision the central gateway: install WireGuard, enable forwarding, generate keys, write the interface config, register peers, lock down the firewall, and bring the tunnel up.

Open the required Security Group ports

Before installing anything, allow inbound traffic on the AWS Security Group attached to the EC2 instance:

ProtocolPortPurpose
UDP51820WireGuard VPN
TCP22SSH
TCP443WSTunnel (Phase 3)
TCP80Optional HTTP

Install WireGuard

bash
sudo apt update
sudo apt upgrade -y
sudo apt install wireguard -y
wg --version

Enable IP forwarding

Required so the server can route packets between VPN peers and subnets.

bash — temporary
sudo sysctl -w net.ipv4.ip_forward=1
bash — permanent
sudo nano /etc/sysctl.conf
# uncomment or add:
net.ipv4.ip_forward=1

sudo sysctl -p
cat /proc/sys/net/ipv4/ip_forward   # expect: 1

Generate server keys

bash
sudo mkdir -p /etc/wireguard
cd /etc/wireguard
wg genkey | sudo tee server_private.key | wg pubkey | sudo tee server_public.key
sudo chmod 600 server_private.key
cat server_public.key
Save the public key output — every client configuration will need it.

Create the server interface config

Note the three Address lines — one interface serves all three logical networks.

/etc/wireguard/wg0.conf
[Interface]
Address = 192.168.100.1/24,192.168.150.1/24,192.168.200.1/24
ListenPort = 51820
PrivateKey = <SERVER_PRIVATE_KEY>
DNS = 192.168.150.40

Add a [Peer] block for every client

Each client gets its own unique /32 address.

append to wg0.conf
# MISP
[Peer]
PublicKey = <KEY>
AllowedIPs = 192.168.150.10/32

# SOC Core
[Peer]
PublicKey = <KEY>
AllowedIPs = 192.168.150.20/32

# IDS
[Peer]
PublicKey = <KEY>
AllowedIPs = 192.168.150.30/32

# AD-DS
[Peer]
PublicKey = <KEY>
AllowedIPs = 192.168.150.40/32

# Honeypot
[Peer]
PublicKey = <KEY>
AllowedIPs = 192.168.100.100/32
Never set AllowedIPs = 192.168.100.0/24 on an individual peer — a whole subnet on one peer causes ambiguous routing. Always use a single host /32.

Configure nftables (firewall + NAT)

/etc/nftables.conf
table inet filter {
  chain input {
    type filter hook input priority filter;
    policy drop;
    iif "lo" accept
    ct state established,related accept
    iifname "wg0" accept
    tcp dport 22 accept
    udp dport 51820 accept
    ip protocol icmp accept
  }
  chain forward {
    type filter hook forward priority filter;
    policy drop;
    iifname "wg0" accept
    ct state established,related accept
  }
  chain output {
    type filter hook output priority filter;
    policy accept
  }
}
table ip nat {
  chain postrouting {
    type nat hook postrouting priority srcnat;
    policy accept;
    oifname "ens5" masquerade
  }
}
bash — apply & verify
sudo systemctl enable nftables
sudo systemctl restart nftables
sudo nft list ruleset

Start WireGuard

bash
sudo systemctl enable wg-quick@wg0
sudo systemctl start wg-quick@wg0
# or manually:
sudo wg-quick up wg0

Verify the server

bash
ip addr show wg0
sudo wg show

Peers will appear with no handshake until a client actually connects — that's expected at this stage.

Reference: useful server commands

bash
sudo wg-quick up wg0        # bring up
sudo wg-quick down wg0      # bring down
sudo systemctl restart wg-quick@wg0
sudo systemctl status wg-quick@wg0
sudo journalctl -u wg-quick@wg0

Sends a keepalive every 25s to maintain NAT mappings for clients behind routers/firewalls.

Public IP:port today. Changes to 127.0.0.1:51820 after Phase 3 (WSTunnel).

ping 192.168.150.20       # another VPN client (cross-subnet)

P3

WSTunnel Integration (HTTPS Transport) & Routing Fix

A FortiGate firewall in the environment blocked UDP 51820 and ICMP. WSTunnel encapsulates the WireGuard UDP packets inside HTTPS (TCP 443) so the same VPN survives restrictive networks — no change to WireGuard addressing or peers, only the transport.

Install WSTunnel (both server and client hosts)

bash
cd /tmp
wget https://github.com/erebe/wstunnel/releases/download/v10.6.2/wstunnel_10.6.2_linux_amd64.tar.gz
tar -xzf wstunnel_10.6.2_linux_amd64.tar.gz
sudo mv wstunnel /usr/local/bin/
sudo chmod +x /usr/local/bin/wstunnel
wstunnel --version   # expect: wstunnel-cli 10.6.2

Server: create the WSTunnel systemd service

/etc/systemd/system/wstunnel.service
[Unit]
Description=WSTunnel Server
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/wstunnel server \
  wss://0.0.0.0:443
Restart=always
RestartSec=5
User=root

[Install]
WantedBy=multi-user.target
bash
sudo systemctl daemon-reload
sudo systemctl enable wstunnel
sudo systemctl start wstunnel
sudo systemctl status wstunnel

Server: open HTTPS in nftables

nftables — add rule
tcp dport 443 accept
bash — apply & test
sudo systemctl restart nftables
curl -vk https://13.205.137.92:443
An HTTP 400 Invalid request response is expected here — WSTunnel only accepts WebSocket upgrade requests, not plain GETs. That 400 confirms the service is reachable.

Client: point WireGuard at localhost

client wg0.conf — change
# before
Endpoint = 13.205.137.92:51820

# after
Endpoint = 127.0.0.1:51820

Client: create the WSTunnel client service

/etc/systemd/system/wstunnel.service
[Unit]
Description=WSTunnel Client
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/wstunnel client \
  -L udp://51820:127.0.0.1:51820?timeout_sec=0 \
  wss://13.205.137.92:443
Restart=always
RestartSec=5
User=root

[Install]
WantedBy=multi-user.target
bash
sudo systemctl daemon-reload
sudo systemctl enable wstunnel
sudo systemctl start wstunnel

Verify WSTunnel on both ends

bash
sudo systemctl status wstunnel
sudo journalctl -u wstunnel -f
sudo ss -lunp | grep 51820   # expect: 127.0.0.1:51820

The routing-loop problem (and why it happens)

With AllowedIPs = 0.0.0.0/0, WireGuard installs a default route sending everything through wg0 — including WSTunnel's own outbound HTTPS connection to the AWS endpoint. That creates an infinite loop: WSTunnel → wg0 → WSTunnel → wg0…

Symptoms: no handshake, continuous retransmissions, TX increasing while RX stays at zero, and the WSTunnel TCP connection timing out.

Confirm the diagnosis:

bash
sudo wg-quick down wg0
nc -vz 13.205.137.92 443   # succeeds with wg0 down

sudo wg-quick up wg0
nc -vz 13.205.137.92 443   # times out with wg0 up

Fix: static host route around the tunnel

Route traffic to the AWS public IP via the physical interface so it never re-enters wg0.

bash — manual test
sudo ip route add 13.205.137.92/32 via 192.168.74.254 dev ens33
ip route   # expect: 13.205.137.92 via 192.168.74.254 dev ens33

Make it permanent by adding it to the WireGuard config itself:

append to wg0.conf
PostUp = ip route add 13.205.137.92/32 via 192.168.74.254 dev ens33
PostDown = ip route del 13.205.137.92/32 via 192.168.74.254 dev ens33
Replace 192.168.74.254 / ens33 with your own physical gateway and interface name.

Restart everything and validate

bash
sudo systemctl restart wstunnel
sudo systemctl restart wg-quick@wg0
sudo wg show
ip route
ping 192.168.100.1
sudo journalctl -u wstunnel

Expect a fresh handshake with growing RX/TX, the static host route present alongside the default route, and WSTunnel logs showing accepted WebSocket connections rather than timeouts.

Windows Server Client Configuration

Same WireGuard architecture and the same WSTunnel-over-HTTPS transport, on Windows Server 2022 — WireGuard talks to WSTunnel locally over 127.0.0.1:51820, and WSTunnel carries it out over TCP 443.

Install the WireGuard for Windows client

Download and install the official client, launch it, create a new empty tunnel, and let it generate a key pair. Copy the generated public key.

Register the Windows peer on the server

on server — /etc/wireguard/wg0.conf
[Peer]
PublicKey = WINDOWS_PUBLIC_KEY
AllowedIPs = 192.168.150.40/32
bash — on server
sudo systemctl restart wg-quick@wg0

Configure the Windows WireGuard tunnel

WireGuard GUI — tunnel config
[Interface]
PrivateKey = WINDOWS_PRIVATE_KEY
Address = 192.168.150.40/24
DNS = 192.168.150.40

[Peer]
PublicKey = SERVER_PUBLIC_KEY
Endpoint = 127.0.0.1:51820
AllowedIPs = 0.0.0.0/0
PersistentKeepalive = 25
The endpoint is 127.0.0.1:51820, not the AWS public IP — WSTunnel handles the real network hop.

Install WSTunnel for Windows

Download the Windows AMD64 release and extract to C:\wstunnel\wstunnel.exe.

Test WSTunnel manually first

cmd — run as Administrator
C:\wstunnel\wstunnel.exe client ^
  -L udp://51820:127.0.0.1:51820?timeout_sec=0 ^
  wss://13.205.137.92:443

If it starts cleanly with no errors, proceed to make it a service.

Wrap it as a Windows service with NSSM

cmd — elevated
nssm install WSTunnel
FieldValue
ApplicationC:\wstunnel\wstunnel.exe
Startup directoryC:\wstunnel
Argumentsclient -L udp://51820:127.0.0.1:51820?timeout_sec=0 wss://13.205.137.92:443
cmd

Known blocker: missing Visual C++ Runtime

If WSTunnel exits immediately with no logs and NSSM reports failures, the Microsoft Visual C++ Redistributable (2015–2022 x64) is missing.

Fix: install VC_redist.x64.exe, reboot the server, then restart the WSTunnel service.

Allow the right traffic through Windows Firewall

WireGuard WSTunnel Loopback (127.0.0.1) Outbound HTTPS (443)

No inbound UDP 51820 rule is required — WireGuard only ever talks to WSTunnel locally.

Validate

cmd
sc query WSTunnel
ping 192.168.100.1
ping 192.168.150.20
nslookup <internal-hostname>

In the WireGuard GUI: tunnel active, latest handshake updating, RX/TX counters climbing.

Troubleshooting

Click a symptom to expand cause and fix.

No WireGuard handshakecommon+

Possible causes: incorrect server/client keys, peer not added on the server, WSTunnel not running, wrong endpoint (should be 127.0.0.1:51820 after WSTunnel is in place), or TCP 443 blocked upstream.

Check: sudo wg show on both ends, and confirm the peer's public key matches exactly.

WSTunnel connection times out through the VPNrouting loop+

Cause: AllowedIPs = 0.0.0.0/0 routes WSTunnel's own outbound connection back through wg0, creating a recursive loop.

Fix: add a static host route to the AWS public IP via the physical interface (PostUp/PostDown in wg0.conf). See Phase 3, step 8.

curl to https://<server>:443 returns "HTTP 400 Invalid request"expected+

This is not an error. WSTunnel only accepts WebSocket upgrade requests, not plain HTTPS GETs — a 400 confirms the service is up and reachable on 443.

WSTunnel fails to start on Windowsmissing runtime+

Symptoms: process exits immediately, NSSM reports service failures, no WSTunnel logs are produced.

Cause: the Microsoft Visual C++ Redistributable (2015–2022 x64) is not installed.

Fix: install VC_redist.x64.exe, reboot, restart the service.

NSSM service won't stay runningdependency+

Cause: same VC++ runtime dependency issue causing wstunnel.exe to terminate immediately.

Fix: install the runtime, then recreate or restart the NSSM service.

WSTunnel client can't connect to the server at allconnectivity+

Checklist:

• AWS Security Group allows inbound TCP 443
• wstunnel.service is running on the server (systemctl status wstunnel)
• nc -vz <server_ip> 443 succeeds from the client
• the static host route for the AWS public IP exists (Linux full-tunnel clients)

08

Design Decisions, Advantages & Limitations

DecisionReason
AWS-hosted VPN serverCentralized, secure access point
Multiple subnets on one interfaceSimplified routing and scalability
Static peer addressingPredictable management and ACLs
Public-key authenticationEliminates shared secrets
Full-tunnel (0.0.0.0/0)Centralized traffic routing
DNS via AD-DSUnified name resolution and domain integration

Advantages

Lightweight, low latency, high throughput, minimal config overhead, strong modern cryptography, easy peer management, cross-platform (Linux + Windows), scales to multiple private networks, centralized SOC gateway.

Limitations

Native UDP 51820 may be blocked by enterprise firewalls (hence WSTunnel). Full-tunnel routing needs careful route management to avoid loops. Public-key distribution must be managed securely. WireGuard itself has no built-in centralized identity management — authorization is purely by configured public key.

Key findings:

A single WireGuard interface can host multiple IP subnets, letting one gateway serve several logical networks at once.

A unique /32 AllowedIPs per peer guarantees deterministic routing and avoids address conflicts.

PersistentKeepalive = 25 keeps NAT mappings alive for clients behind NAT or restrictive firewalls.

Integrating the VPN with AD-DS DNS (192.168.150.40) gives centralized name resolution for domain-joined and VPN-connected hosts.

WSTunnel extends the same WireGuard deployment to run over HTTPS wherever native UDP is blocked, without changing the underlying VPN design.
