Implementation Report

Tunneling WireGuard through a firewall
that only trusts port 443

The org firewall blocked UDP/51820 and ICMP outright, so on-prem machines could never reach the AWS WireGuard server directly. WSTunnel wraps the WireGuard UDP stream inside a WebSocket-over-TLS connection — traffic the firewall already lets through — and hands it back to WireGuard on the other side.

01

Objective

The organization firewall blocked native WireGuard UDP (51820) traffic, preventing on-premises virtual machines from connecting to the AWS VPN server. WSTunnel was implemented to encapsulate WireGuard UDP packets inside WebSocket over HTTPS (TCP 443), letting VPN traffic traverse restrictive firewalls while keeping the connection encrypted end to end.

Solution architecture

Server side — WSTunnel terminates the WebSocket/TLS connection on EC2 and hands the decoded UDP stream to the local WireGuard server:

Internet │ HTTPS (TCP 443) │ ┌────────────────────┐ │ AWS EC2 │ │ WSTunnel Server │ └────────────────────┘ │ localhost:51820 │ WireGuard Server │ ┌───────────────┬───────────────┬───────────────┐ 192.168.100.x 192.168.150.x 192.168.200.x

Client side — WireGuard never talks to AWS directly; it talks to WSTunnel on localhost, which does the real network hop:

WireGuard Client │ localhost:51820 │ WSTunnel Client │ HTTPS (443) │ AWS EC2

Server configuration

WireGuard — interface wg0, listening on UDP 51820, bound to 192.168.100.1/24, 192.168.150.1/24, 192.168.200.1/24. Each VPN client is a peer keyed by its public key with a /32 AllowedIPs entry.

WSTunnel server — installed as a systemd service:

wstunnel server \
  --restrict-to localhost:51820 \
  wss://0.0.0.0:443
Listens on HTTPS 443, accepts WebSocket connections, forwards decrypted UDP packets to the local WireGuard server only.
07

Client configuration

WireGuard endpoint is set to 127.0.0.1:51820 — WireGuard talks locally to WSTunnel instead of directly to AWS.

wstunnel client \
  -L udp://51820:localhost:51820?timeout_sec=0 \
  wss://13.205.137.92:443
WireGuard │ localhost:51820 │ WSTunnel │ HTTPS 443 │ AWS
08

Routing configuration

Initially: AllowedIPs = 0.0.0.0/0 routed the entire system into the VPN — including WSTunnel's own HTTPS packets, which then tried to traverse the very tunnel they were responsible for establishing. Routing loop, connection timeouts.

Fix: add a static route for the AWS endpoint before bringing WireGuard up, so it bypasses the tunnel:

ip route add 13.205.137.92/32 via <physical_gateway> dev <physical_interface>
Result: traffic to the AWS public IP goes out the physical interface directly; everything else still rides the VPN.

Firewall configuration

AWS security group — allowed inbound:

nftables (host firewall) permits SSH, ICMP, WireGuard UDP, WSTunnel HTTPS, VPN forwarding, and NAT masquerading. The HTTPS rule was only added after discovering inbound TCP 443 was being silently dropped at the host level, despite the security group already allowing it.

14

Key findings

  • WSTunnel effectively bypassed the organizational UDP restriction by tunneling WireGuard traffic through HTTPS (TCP 443).
  • A full-tunnel WireGuard config (AllowedIPs = 0.0.0.0/0) introduced a routing loop that stopped WSTunnel reaching AWS; a static host route resolved it.
  • The server's --restrict-to option must explicitly name the local UDP destination (localhost:51820) or forwarding to WireGuard won't happen.
  • curl returning "Invalid request" confirmed the HTTPS listener was reachable — it doesn't validate WSTunnel itself, since WSTunnel needs a WebSocket upgrade, not a plain GET.
  • On Windows, the Microsoft Visual C++ Runtime is a hard dependency for wstunnel.exe.
  • Running WSTunnel as a persistent service (systemd / NSSM) ensured automatic startup and reliable operation on both platforms.
  • End state: Linux and Windows clients join the private VPN over TCP 443 with no WireGuard UDP ever exposed to the internet.

Step-by-step implementation

A straight-through build order — server first, then Linux client, then Windows client. Each step is what to run and why it matters; skip to the checklist if you just need to confirm a working setup.

Before you start
A working WireGuard VPN already deployed on the EC2 host (wg0, UDP 51820) · root/sudo on server and clients · AWS security group open on 443 · WSTunnel v10.6.2 release binary

Stage A — AWS EC2 server5 steps
S1

Confirm WireGuard is already up

Don't touch WSTunnel until the base VPN is verified healthy.

sudo wg show
# expect: interface wg0, listening port 51820, peers listed
Why: if WireGuard itself is broken, layering a tunnel on top only hides the real problem.
S2

Free up port 443

sudo ss -tlnp | grep :443
# expect: no output

If downloading the release hits Temporary failure in name resolution, WireGuard's own DNS config is likely interfering — drop the interface, fetch the binary, then continue:

sudo wg-quick down wg0
dig www.google.com   # confirm DNS works again
S3

Install WSTunnel

cd /tmp
wget https://github.com/erebe/wstunnel/releases/download/v10.6.2/wstunnel_10.6.2_linux_amd64.tar.gz
tar -xzf wstunnel_10.6.2_linux_amd64.tar.gz
sudo mv wstunnel /usr/local/bin/
sudo chmod +x /usr/local/bin/wstunnel
wstunnel --version   # wstunnel-cli 10.6.2
Why pin v10.6.2: GitHub's "latest" redirect can point past a filename you already have cached — verify the real tag first with the GitHub API if wget 404s.
S4

Test the server, then open the firewall

sudo wstunnel server \
  --restrict-to localhost:51820 \
  wss://0.0.0.0:443

A local curl -vk https://127.0.0.1:443 returning HTTP/2 400 Invalid request means it's working — WSTunnel rejects plain GETs by design. If a remote curl from off-box times out, check nftables, not just the AWS security group:

sudo nft list ruleset            # look for policy drop + missing tcp/443
sudo nft add rule inet filter input tcp dport 443 accept
S5

Run it as a service

Stop the foreground process (Ctrl-C) and create /etc/systemd/system/wstunnel.service:

[Unit]
Description=WSTunnel Server
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/wstunnel server \
  --restrict-to localhost:51820 \
  wss://0.0.0.0:443
Restart=always
RestartSec=5
User=root

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now wstunnel
sudo systemctl status wstunnel      # Active: active (running)
sudo journalctl -u wstunnel         # Listening on 0.0.0.0:443 · Server ready.

L1

Install WSTunnel

uname -m && cat /etc/os-release

L2

Point WireGuard at localhost, start WSTunnel client

In the client's WireGuard config, change Endpoint = 13.205.137.92:51820 to Endpoint = 127.0.0.1:51820. Then, before bringing WireGuard up, start the tunnel:

wstunnel client \
  -L udp://51820:127.0.0.1:51820?timeout_sec=0 \
  wss://13.205.137.92:443
sudo ss -lunp | grep 51820   # expect 127.0.0.1:51820, process wstunnel
L3

Fix the routing loop before going full-tunnel

If the peer's AllowedIPs = 0.0.0.0/0, WSTunnel's own HTTPS traffic will try to ride the VPN it's building. Add a static host route for the AWS IP through the physical interface first:

sudo ip route add 13.205.137.92/32 via <physical_gateway> dev <physical_interface>
# e.g. sudo ip route add 13.205.137.92/32 via 192.168.74.254 dev ens33

Persist it so it survives every WireGuard restart — add to wg0.conf:

PostUp = ip route add 13.205.137.92/32 via 192.168.74.254 dev ens33
PostDown = ip route del 13.205.137.92/32 via 192.168.74.254 dev ens33
Why this order matters: do this before the first wg-quick up with a full-tunnel config, or you'll chase a "0 B received" handshake failure that's actually a routing loop, not a WireGuard problem.
L4

Run the client as a service

/etc/systemd/system/wstunnel.service:

[Service]

RestartSec=5
User=root

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now wstunnel

End-to-end checklistverify the build
  • Server: systemctl status wstunnel is active, ss -tlnp shows 443 listening, wg show shows the interface up.
  • Firewall: nftables allows tcp/443 inbound; AWS security group allows 443, 51820, 22, 80.
  • Client transport: nc -vz <server-ip> 443 succeeds; ss -lunp | grep 51820 shows WSTunnel bound to localhost.
  • Routing: a static /32 route to the server's public IP exists via the physical interface, persisted through PostUp/PostDown.
  • Handshake: wg show on the client shows a recent handshake with both RX and TX increasing, not just TX.
  • Reachability: ping to a VPN-side address (e.g. 192.168.100.1) succeeds.
  • Persistence: both server and client WSTunnel processes are registered services (systemd / NSSM), not foreground shells.
